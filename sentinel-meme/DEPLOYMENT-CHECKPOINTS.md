# SENTINEL — Render + Windows deployment candidate

This extends the existing Python engine. Live submission is disabled in `Providers.execute`, cloud mode selection, and Windows setup. Do not fund the generated wallet. Local paper tests are not a security certification or a profitability result.

## What runs without your phone

`service.py` runs the authenticated dashboard alongside `cloud.py` and continuous market-discovery threads. Closing Safari has no effect on those processes. Render must use paid always-on compute and its persistent disk. A PC must remain powered, awake, connected, and running the supervisor. Your iPhone needs internet only when you view/control the dashboard; its connection does not keep the server alive.

The existing engine retains finalized Solana wallet subscriptions, known-developer outflow checks, mint/freeze authority checks, concentration/liquidity/age gates, quote-cost gates, entry limits, exits, and Telegram alerts. These are limited checks, not proof a coin cannot rug. Wallet signal decoding currently recognizes the supported Jupiter swap pattern; it does not decode every Pump.fun or Axiom trade.

DexScreener discovery polls every 30 seconds. Pump.fun new-token discovery uses the third-party PumpPortal feed when `PUMPPORTAL_API_KEY` is configured. Provider failures are visible; cached records are not guaranteed current. PumpPortal discovery never authorizes an order. Paid account/token trade subscriptions are not enabled. There is no Axiom private feed or Phantom unattended signing integration in this release.

## Shared ownership — mandatory before either host trades

Both installations MUST point to the **same PostgreSQL database**. A persistent deployment UUID pins that database to the first configured execution host. An advisory lock prevents a second execution session with that UUID. A different host remains standby even when the original disconnects. A missing/unreachable coordinator blocks paper buys, sells, and recovery. The original host may reconnect automatically. Use direct PostgreSQL connections, not transaction-pooled connections.

This deliberately does not automatically fail over across two independent SQLite ledgers. Standby has its own history and cannot safely manage the active host's positions. Do not clone a running data directory, delete `deployment-id`, reset the coordinator table, or change database URLs to bypass standby. For migration: pause entries, close and reconcile all positions, stop BOTH hosts, take a consistent full data-directory backup, and review migration before changing pinned ownership. A new independent database removes cross-host coordination.

## Render deployment checkpoint

1. Apply **repository-root `render.yaml`** in the confirmed Render workspace **Trading Bot**. The old nested Blueprint is deprecated. The root defines one paid web service, a 1 GB persistent disk, and a small paid PostgreSQL coordinator. Review the actual recurring price shown by Render before Apply; no free sleeping web service or expiring free database.
2. Supply `SOLANA_RPC_URL` (HTTPS), `SOLANA_WS_URL` (WSS), and `JUPITER_API_KEY` in Render's secret environment fields. Never paste secrets in GitHub or chat. Dashboard/vault/pairing secrets are generated by Render. `DASHBOARD_ORIGIN` defaults to Render's documented `RENDER_EXTERNAL_URL`; set it explicitly if using a custom domain.
3. Add optional `TELEGRAM_BOT_TOKEN` and `PUMPPORTAL_API_KEY` through Environment and redeploy. The same Telegram bot token must NOT run on two pollers: use a separate bot for each host, or enable Telegram only on the active host. Without Telegram, in-app activity remains available but phone push alerts are not configured.
4. Wait for successful build/deploy and `/healthz` HTTP 200. Read the generated `DASHBOARD_PASSWORD` securely in Render, then sign in at the assigned service URL. No public API exposes the ledger.
5. In the dashboard set at least three real watched Solana wallets and a known-developer mapping (JSON mint address → array of developer wallet addresses). No wallet selection is supplied automatically. Verify health, feed timestamps, and configured limits before resuming paper entries. No eligible signal means no trade.
6. Restart the service and verify history/positions persist. It deliberately starts with entries paused. A 10-minute worker-heartbeat timeout fails health checks; Render health recovery and deployment downtime must be tested on the actual service.

Render's connector cannot create the required disk or apply this Blueprint; the authenticated Dashboard step is necessary. Do not create a diskless replacement merely to obtain a URL.

## PC checkpoint 1 — install and private network

Stop here for the user's PC actions.

1. Download the updated repository, keeping any existing `%LOCALAPPDATA%\SentinelTradingBot` state intact. Do not overwrite it with example files.
2. Fix the previously reported runtime error: in PowerShell run `py install 3.12`. If your launcher does not support that command, install Python 3.12 from python.org with launcher and Tcl/Tk enabled. Verify `py -3.12 --version`. Python 3.14 alone is not the tested runtime.
3. Install Tailscale on Windows and iPhone. Sign both into the same private tailnet. In an elevated PowerShell from `sentinel-meme`, run `powershell -ExecutionPolicy Bypass -File .\SETUP-TAILSCALE.ps1`. This enables Windows unattended mode and persistent Serve forwarding to loopback port 8765. Follow any Tailscale HTTPS activation prompt. It does not enable public Funnel or require router port forwarding.
4. Record the exact HTTPS origin printed by `tailscale serve status` (no trailing slash). Restrict tailnet access to your own authorized devices in Tailscale policy; review any existing shared users/devices.

Reply with the Python version and whether Tailscale is connected. Do not send credentials. Continue only after this checkpoint is confirmed.

## PC checkpoint 2 — configure and start

1. In Render PostgreSQL Networking allow only the PC's current public IPv4 `/32` (or narrowly scoped IPv6), not `0.0.0.0/0`. The Blueprint starts with no external database access. A changed home public IP will block execution until this rule is updated.
2. Use that same database's **external direct** connection URL on Windows, with `sslmode=require`; the Render service uses its internal connection. Store the URL only in the local setup form.
3. Run `SETUP-WINDOWS.cmd`. Enter the dashboard password (32+ random characters), Tailscale HTTPS origin, coordinator URL and Solana/Jupiter provider credentials. Telegram and PumpPortal are optional. Credentials are encrypted using Windows DPAPI for the current Windows account. Do not use the same Telegram token simultaneously on Render and PC.
4. Save/start. Open the Tailscale HTTPS URL and sign in. Loopback HTTP is for health probes only; secure login cookies require HTTPS. A PC in standby is expected if Render already owns the coordinator. Do not bypass this to make both paper engines trade.
5. Review `host.log`, health, and any blocked reason. Configure the watchlist and known-developer mapping. Resume only when ready. No automatic restart resets the trading ledger or enables new entries.

## PC checkpoint 3 — boot recovery

1. From elevated PowerShell as the SAME account used for setup, run `powershell -ExecutionPolicy Bypass -File .\INSTALL-BOOT-TASK.ps1`. Enter the Windows account password locally, not a Windows Hello PIN. This installs an AtStartup task with that account so DPAPI decryption works before interactive sign-in. Do not run it as SYSTEM or another account.
2. The existing login shortcut and new scheduled task share the supervisor file lock, preventing a second local worker. Disable the login shortcut in setup if desired.
3. Reboot without signing in. Verify Tailscale reachability and dashboard health from another device. Confirm old fills and positions remain and entries are paused. Then sign in on the PC and inspect Task Scheduler's Last Run Result and host log.
4. Briefly disconnect PC internet and reconnect. Confirm disconnected/blocked states, reconnection, and no duplicate fills. Simultaneously keep Render online and confirm only the pinned owner executes.

The supervisor inhibits ordinary automatic sleep while running, but cannot prevent power loss, manual shutdown, hibernation, or loss of internet. Back up state and Windows account recovery material. Do not promise uninterrupted uptime from one PC.

## iPhone checkpoint — only after PC checks pass

1. Enable Tailscale on iPhone; open the exact PC HTTPS URL in Safari and sign in.
2. Turn off Wi-Fi and use cellular data. Verify fresh timestamps and an authenticated pause action. Never expose port 8765 publicly as a workaround.
3. Resume eligible paper entries, close Safari, lock the phone, then return later. Compare durable activity timestamps with the closed-browser interval. A quiet market is not a failed worker; use health and feed observations as well as trades.
4. Confirm Telegram notifications if configured, then repeat after PC reboot. Record elapsed time, errors, and order/fill counts; do not infer success from a page loading once.

## Release gate

No live-mode toggle will enable execution. Before a separate live release: real PostgreSQL contention/outage tests, Windows boot/DPAPI tests, cellular/Tailscale testing, sustained real-feed paper runs, execution simulation/security review, and risk-limit tests must pass. Phantom connection alone cannot authorize unattended server signing. There is no guarantee of profitable trades or a daily trade count.
